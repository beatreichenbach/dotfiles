# Python Conventions

## Package imports / exports

1. Every `__init__.py` that re-exports names must define `__all__` listing
   exactly the public names. Keep re-exports and `__all__` in sync.
2. Use relative imports inside packages (`from .foo import bar`), not absolute
   imports of the package itself.

## Methods

1. Make a method `@staticmethod` when it does not use `self` (or `cls`). Do not
   keep an unused first parameter merely to avoid the decorator.
2. Order members within a class: helper functions, `__init__`, `_init_*`
   helpers (e.g. `_init_thread`, `_init_db`), `get_` methods, `set_` methods,
   public methods, private methods, static methods.

## Module organization

Organize a module in this order:

1. Structs / dataclasses
2. Classes
3. Helper functions

## Project toolchain

Use `uv` for environments and dependencies, `ruff` for formatting and linting,
and `ty` for type checking. Do not use pip/venv directly, black, flake8, isort,
or mypy.

- Create the environment with `uv venv`, install with `uv pip install -e ".[dev]"`,
  and run tools through `uv run` (e.g. `uv run ty check`).
- Commit `uv.lock`.

## pyproject.toml

Base template:

```toml
[project]
name = "package-name"
version = "0.1.0"
description = "..."
authors = [{ name = "Beat Reichenbach" }]
dependencies = []
requires-python = ">=3.9"
license = "GPL-3.0-or-later"
readme = "README.md"

[project.optional-dependencies]
dev = [
    "pre-commit>=4.0",
    "python-semantic-release>=9.0",
    "pytest>=8.0",
    "ruff>=0.16",
    "ty>=0.0.82",
]

[build-system]
requires = ["setuptools"]
build-backend = "setuptools.build_meta"

[tool.setuptools.packages.find]
include = ["package_name*"]

[tool.setuptools.package-data]
package_name = ["py.typed"]

[tool.semantic_release]
allow_zero_version = true
version_variables = ["package_name/__init__.py:__version__"]
version_toml = ["pyproject.toml:project.version"]

[tool.semantic_release.remote]
ignore_token_for_push = true

[tool.ruff.format]
quote-style = "single"

[tool.ruff.lint]
select = ["E", "W", "F", "I", "UP", "B", "SIM", "ANN", "RUF"]

[tool.pytest.ini_options]
log_cli = true
log_level = "INFO"
```

- Add `[tool.ruff]` / `[tool.ty.src]` exclusions for generated resources.
- Keep the `__version__` in the package `__init__.py` in sync with
  `version_variables` so semantic-release can bump it.

## Licensing

Default to GPL-3.0-or-later. MIT is acceptable when a permissive license is
required. Always ship a `LICENSE` file and set `license` in `pyproject.toml`.

## py.typed

Every typed package ships an empty `py.typed` marker inside the package
directory and lists it under `[tool.setuptools.package-data]`.

## Examples and tests

Keep them separate:

- `examples/` holds runnable demonstrations, one script per feature, each with an
  `__init__.py`. They are for humans and are not collected by pytest.
- `tests/` holds pytest modules named `test_*.py` plus a `conftest.py`. Unit
  tests never live in `examples/`.

## CONTRIBUTING.md

Provide a `CONTRIBUTING.md` with development setup and the check commands:

```md
# Contributing Guide

## Development

uv venv --python 3.13
uv pip install -e ".[dev]"
pre-commit install

Run the checks:

ruff format <package> examples tests
ruff check --select I --fix <package> examples tests
ruff check <package> examples tests
ty check
pytest

### Releasing Changes

semantic-release version
```

Also add a `.pre-commit-config.yaml` running `ruff-check`, `ruff-format`, and
`ty check`.

## CHANGELOG.md

Keep a `CHANGELOG.md` generated by python-semantic-release. If it does not exist
yet, generate the empty changelog with the tool, never by hand:

```sh
uv run semantic-release changelog
```

Let semantic-release write releases into it; do not edit the file manually.

## Publishing to PyPI

Publish from GitHub Actions with PyPI Trusted Publishing (OIDC). Do not use
long-lived API tokens or stored `twine` passwords.

1. Trigger on `release: published` so python-semantic-release creates the
   release and the workflow publishes it.
2. Split build and publish into separate jobs. Only the publish job gets
   `id-token: write`; never run build code in the job that holds the OIDC token.
   Pass the built distributions between jobs as an artifact.
3. Give the publish job a GitHub environment (`pypi`) and configure the matching
   PyPI trusted publisher with the owner, repository, workflow filename, and
   environment name.
4. Publish with `pypa/gh-action-pypi-publish`, which generates PEP 740
   attestations by default.
5. Pin actions to a major tag (or a commit SHA for stricter supply-chain
   control) and grant `contents: read` where `actions/checkout` is used.

`.github/workflows/publish.yml`:

```yaml
name: Publish

on:
  release:
    types: [published]

permissions: {}

jobs:
  build:
    name: Build distributions
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@v7
        with:
          persist-credentials: false
      - uses: astral-sh/setup-uv@v10.2.0
      - name: Build sdist and wheel
        run: uv build
      - name: Check distribution metadata
        run: uvx twine check dist/*
      - uses: actions/upload-artifact@v7
        with:
          name: dist
          path: dist/

  publish:
    name: Publish to PyPI
    needs: [build]
    runs-on: ubuntu-latest
    environment:
      name: pypi
      url: https://pypi.org/project/<package-name>/
    permissions:
      id-token: write
    steps:
      - uses: actions/download-artifact@v8
        with:
          name: dist
          path: dist/
      - uses: pypa/gh-action-pypi-publish@release/v1
```

On GitHub, create the `pypi` environment with required reviewers and a tag
restriction. On PyPI, add a trusted publisher for the project (or a pending
publisher for a new project).

## .gitignore

Use GitHub's Python `.gitignore`
(https://github.com/github/gitignore/blob/main/Python.gitignore), keeping the
uv section intact.

## Errors

1. Exception messages are lowercase: they are read by developers in tracebacks
   and often composed into larger messages.
2. Log messages shown to the user are capitalized sentences, e.g.
   `logger.error(f'Could not read file: {path}')`.
3. Log once, at the boundary: library code raises, the CLI/UI layer logs. Never
   log an error you also raise — it double-reports.
